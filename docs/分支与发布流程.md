# 分支与发布流程

> 适用范围：本仓库（FocusStation）采用 **main（生产/稳定基线）+ dev（开发/测试环境）** 双分支模型。
> 依据：《新产品开发手册：MVP → 完整版的工程实践清单》阶段 2.2 / 2.3 / 2.4 与阶段 3.4。
> 本文与代码互锁：`.github/workflows/ci.yml`、`.github/workflows/ops.yml`、`.github/PULL_REQUEST_TEMPLATE.md`。

---

## 1. 分支模型

| 分支 | 角色 | 触发 CI | 直接推送 | 说明 |
|---|---|---|---|---|
| `main` | 生产 / 稳定基线 | PR 时 | ❌ 禁止 | 只接收经 PR 合并、且 CI 全绿的改动 |
| `dev` | 开发 / 测试环境 | push 时 | ✅ 允许 | 所有新功能先在此开发、验证，稳定后提 PR 合回 main |

> 当前 `main` 与 `dev` 同处于提交 `e1fc219`（main 为 dev 的快进基线）。`dev` 上新增提交后，通过 PR 合入 `main`。

## 2. 环境标记（手册 2.3 测试消息打标体系）

- `dev` 与 PR 均视为**非生产环境**：CI 自动注入 `PUSH_TEST=1` / `APP_ENV=test`，同一套凭据下测试与生产推送一眼区分。
- `main` 为**生产守卫**：禁止手动触发运维 workflow（见 §4 守卫），且不允许直接 `git push`（须经 PR）。
- 若将来接入真实推送通道，生产入口需加「禁止手动触发」守卫，dev 的测试推送带 `[测试]` 前缀。

## 3. 持续集成（手册 2.2 / 2.4 / 1.5 / 1.6）

文件：`.github/workflows/ci.yml`，运行于 `windows-latest`（与本地 Windows 编译环境一致）。

- **触发**：`push` 到 `dev`，或向 `main` 提 `pull_request`。
- **并发防护（2.2）**：`concurrency.group = ci-<workflow>-<ref>`，`cancel-in-progress: false`（在途运行不被取消，避免丢状态）。
- **可审计（2.4）**：`checkout` 用 `fetch-depth: 0`，保留完整版本历史，可回放、可回滚。
- **构建/测试（1.5/1.6）**：依次跑 `scripts/build.ps1` → `scripts/test.ps1`。测试以**退出码**判定（逻辑 137 assertions + UI 渲染 + 界面单测），不写 mock；隔离目录 `artifacts/work`，与用户数据（`%LocalAppData%\LittleFocusDesktop`）无关。
- **失败即红**：构建或测试任一非零退出，CI 失败、PR 不可合并。

> 注：GitHub Actions 需仓库开启（Settings → Actions → Allow all actions）。若 runner 为无显示器环境，UI 渲染测试依赖离线位图渲染；若实测失败，回此文档记录并调整（如 UI 测试改为非阻塞或自托管 runner）。

## 4. 运维入口（手册 3.4）

文件：`.github/workflows/ops.yml`，手动 `workflow_dispatch` 触发，支持参数：

| 参数 | 取值 | 说明 |
|---|---|---|
| `mode` | `build` / `test` / `build+test` | 必填，运行内容 |
| `note` | 任意字符串 | 可选，仅记录不执行 |

**生产守卫**：`ops.yml` 首步校验 `github.ref_name != main`，在 `main` 上手动触发直接失败退出。运维操作一律在 `dev` 进行。

## 5. 合并 / 发布流程

1. 在 `dev` 开发并自测：`pwsh scripts/build.ps1` + `pwsh scripts/test.ps1` 全绿。
2. 提交 `dev`，推送触发 CI；CI 必须全绿。
3. 从 `dev` 向 `main` 提 PR，按 `PULL_REQUEST_TEMPLATE.md` 逐项勾选。
4. PR CI 全绿后合并（推荐 squash 或 merge，保持 main 线性可读）。
5. 合并后 `main` 即新的稳定基线；`dev` 继续向前。

**冲突处理（手册 2.4）**：`git pull --rebase` 解并发写冲突，不制造无谓 merge commit；状态变化走提交历史，可回放调试。

## 6. 本地约定（非手册，但影响推送）

- 代理：本机出 GitHub 经本地代理（Clash/v2ray 等），端口随客户端重启可能变化（曾 `10137` → `7890`）；推送前确认端口，`git` 全局 `http.proxy`/`https.proxy` 指到当前端口。
- 凭据：GitHub 令牌由 Git Credential Manager 存于本机凭据管理器，需带 `repo` 范围；只读令牌会 403。
- 推送命令示例：`git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push origin main dev`

## 7. 构建产物命名（保险）

`scripts/build.ps1` 按当前分支自动命名输出，确保 dev 构建**不会覆盖** main 产物：

- `main` → `artifacts/FocusStation-v2.0.10.exe`
- 其他分支（如 `dev`）→ `artifacts/FocusStation-v2.0.10-<分支名>.exe`（例：`FocusStation-v2.0.10-dev.exe`）
- 分支判定直接读 `.git/HEAD`，不依赖 git 命令行是否在 PATH 上。

> 用户运行 main 软件时，认准 `FocusStation-v2.0.10.exe`；dev 产物同名不同后缀，互不干扰。
